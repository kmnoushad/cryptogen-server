# v6.9.17 — separate Binance execution worker

Railway runs `npm start`: Futures, Alpha, pump-fade detector, paper tests,
market reports and the sole Telegram command poller. It does NOT import or
instantiate the signed Binance client. Even leftover ENABLE_FADE_EXECUTION=true
cannot activate local orders. Remove Binance credentials from Railway after cutover.

AWS runs `npm run start:fade`: existing Binance reconciliation/protection plus
fresh signal consumption, no market scanners, HTTP server or Telegram polling.
It sends execution notifications through the existing Telegram bot.
Supabase remains the shared event journal, runtime lease, control and status store.
This isolates process crashes, not a shared Supabase or Telegram outage.

## Prepare without placing orders

1. Check Binance directly for positions/open orders. Before moving any existing
   execution, pause entries and confirm orders/positions are accounted for.
   Deploy v6.9.17 on Railway before starting the AWS executor. Do not run the
   old v6.9.16 executor alongside the new worker. Keep the same database/account
   and runtime scope so journaled positions can be recovered.
2. In Supabase SQL Editor run `sql/fade_execution.sql` (if not already applied),
   then `sql/fade_worker.sql`. The migration preserves jobs and creates initially
   PAUSED control rows. It uses RLS and service-role-only table/RPC permissions.
3. On Railway retain current alert variables, set FADE_ENVIRONMENT to the worker's
   environment (testnet for demo; live for live controls), ENABLE_PUMP_FADE_ALERTS=true,
   and ENABLE_FADE_EXECUTION=false. Start command stays `npm start`.
   Bad/missing remote database configuration affects fade controls, not boot.
4. Create an AWS Lightsail Linux/Ubuntu dual-stack instance in a region where
   Binance permits API access for your account. Do not use hosting to evade
   geographic/account restrictions. Use a supported Node LTS (22 or 24), git and
   npm; confirm `node --version` and `command -v node`.
5. Lightsail → Networking → Create static IP → attach to this instance in the
   same region. Whitelist its numeric IPv4 on the Binance key, enable Reading
   and Futures only. Verify actual outbound IPv4 from this host, including after
   a restart. No public application port is required; allow SSH only from your
   administrative IP, plus necessary outbound HTTPS/DNS access.
   AWS instructions: https://docs.aws.amazon.com/lightsail/latest/userguide/lightsail-create-static-ip.html
6. Clone this repository at `/opt/nexio` using your normal GitHub authentication
   if private. Deploy the reviewed v6.9.17 commit (not an unreviewed moving branch).
   Run `npm ci --omit=dev` there. Create a system user named `nexio` with read
   access to the repository. On a fresh Ubuntu instance:

   ```sh
   sudo useradd --system --user-group --no-create-home --shell /usr/sbin/nologin nexio
   sudo chown -R root:nexio /opt/nexio
   sudo chmod -R g+rX /opt/nexio
   ```

   Do not copy secrets into the checkout.
7. Copy `deploy/fade-worker.env.example` to `/etc/nexio-fade.env`. Edit it privately
   on AWS with the same Supabase and Telegram credentials and Binance DEMO keys
   first. Restrict it to root ownership, mode 600. Never commit it or paste it in chat.
   The service reads this file as root before running as `nexio`:

   ```sh
   sudo install -m 600 -o root -g root /opt/nexio/deploy/fade-worker.env.example /etc/nexio-fade.env
   sudo nano /etc/nexio-fade.env
   ```

   Run the install command only for initial setup; it replaces that file.
8. Run the read-only check on AWS (Node >=22):

   ```sh
   cd /opt/nexio
   sudo /usr/bin/node --env-file=/etc/nexio-fade.env scripts/fade-preflight.js
   ```

   If Node is installed elsewhere, use that absolute path here AND in the service.
   The check reads Binance and the worker tables; it does not place orders or
   change account modes. It is not a live execution acceptance test.
9. Install the service:

   ```sh
   sudo cp /opt/nexio/deploy/nexio-fade.service /etc/systemd/system/nexio-fade.service
   sudo systemctl daemon-reload
   sudo systemctl enable --now nexio-fade
   sudo systemctl status nexio-fade
   sudo journalctl -u nexio-fade -n 50 --no-pager
   ```

   Start disabled. `/fadeauto` on Telegram must show a recent external worker
   heartbeat and Disabled in the worker report. A heartbeat does not prove API
   access: also inspect last reconciliation/error.

## Demo acceptance and live cutover

For demo, set ENABLE_FADE_EXECUTION=true in the AWS environment file and restart
the service. It monitors/reconciles but new entries remain paused in Supabase.
Send `/faderesume` on Telegram to request entries. Observe a fresh signal,
SELL fill, verified native stop, reduce-only partial limit, partial fill, runner
stop and recovery across restart. Exercise `/fadepause` and `/fadecloseall`.
Confirm actual exchange position/order state; delivery of a command is not execution.

After demo acceptance, flatten and reconcile demo positions before switching.
Set both Railway and worker FADE_ENVIRONMENT=live, put live sub-account credentials
only on AWS, and set FADE_LIVE_ACKNOWLEDGEMENT=I_ACCEPT_LIVE_FADE_ORDERS on AWS.
Run preflight again before enabling the worker. The live control row starts paused;
use `/fadeauto`, then explicitly `/faderesume` when ready.
Keep one worker. The existing renewable lease and revision checks fence duplicate
executors; unknown order acceptance is reconciled, not blindly submitted again.

No AWS instance, keys, SQL migration, demo orders or live orders were provisioned
by this change. These need your AWS/Supabase/Binance account setup.

## Controls and failure behavior

- `/fadepause`: persistently withhold new entries; exchange protection monitoring continues.
- `/faderesume`: request entries; worker must still be enabled and pass reconciliation.
- `/fadecloseall`: pause and request closure of bot-owned positions only. Persists
  across worker downtime; pending until Binance confirms closure.
- `/pause`: pauses Railway scanning and requests external fade pause. `/resume`
  resumes Railway only; `/faderesume` is separate.
- `/fadeauto`: requested state plus worker heartbeat/report. After 60 seconds
  without a heartbeat, reports stale/offline, not zero positions or successful closure.
- `/fadebalance`: cached wallet balance, open PnL, equity, available balance,
  margin in use, progress versus `FADE_START_BALANCE_USDT` (default $100), and
  the latest seven-day realized/commission/funding totals. Binance credentials
  remain on AWS; Railway receives only the sanitized heartbeat report.

Only a new FADE_WORKER_SIGNAL_V1 event, published after successful warning delivery,
can enter execution. Existing warning history/other signals never execute. Events
created before worker startup or with candles older than 90 seconds are skipped.
Signals observed while paused or slots full are not queued for later. The runtime
journal provides durable entry deduplication. Supabase control is re-read before
each entry and immediately before sending the order; an entry already in flight
cannot be undone by a later pause request.

If Railway stops, AWS still manages existing positions (no new alerts arrive).
If control/event reads fail, new entries stop; the independent reconciliation
attempt still runs. If the runtime database or Binance fails, protection updates
can fail too: confirmed native stop/limit orders remain on Binance, but software
trailing/closure is not guaranteed. Check Binance directly during outages.
The optional seven-day income refresh runs outside the protection cycle. A cycle
that nevertheless remains busy for more than 45 seconds exits with an error so
systemd's `Restart=on-failure` policy restarts the worker automatically.
Disabling ENABLE_FADE_EXECUTION stops monitoring as well as entries; use
`/fadepause` to keep managing open positions.

## Capital and strategy scope

This release moves execution only. Existing 2x isolated sizing, max 3 positions,
$150 per-position/$450 aggregate entry notional caps, planned $5 stop and roughly
$3 net partial target are unchanged. The displayed $250 is the intended allocation,
not a balance read. Your $100 deposit is sized down by available-margin checks,
but the $5 planned loss is NOT scaled down: three losses are $15 before excess
slippage/funding. There is no daily loss cap. This change adds no claim of a
profitable strategy and no stock-token scanner; that request remains separate.

Rollback: stop AWS first and account for every Binance position/order. Do not
restore v6.9.16 on Railway with execution enabled or delete runtime tables.
Keep v6.9.17 Railway alerts running if only the worker needs repair.

## v6.9.22 BTC short-entry gate

The AWS worker requires 120 consecutive fresh closed BTCUSDT 1m candles.
New shorts require negative 15m and 30m returns, price below EMA20, and EMA20
falling over five minutes. Mixed/bullish conditions or unavailable data block
new entries. An ask rise of at least 0.35% versus the close three minutes
before the latest close, or 0.20% versus the latest close, also blocks entry.
The live BTC ask must remain below EMA20. These conservative thresholds
are initial risk filters, not empirically validated profitability claims.

The gate runs before sizing and again before the entry POST. It does not stop
reconciliation, cancel protection or close existing trades on a BTC change.
The status line records the last entry check with a timestamp; it is not a
continuous market feed. No SQL or new environment variable is needed.
Keep /fadepause active for deployment and validate in testnet before live use.
This update adds no daily loss cap or guarantee against an altcoin squeeze.
