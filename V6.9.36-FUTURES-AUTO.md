# v6.9.36 — separate-account LONG/SHORT Futures execution

This worker scans and executes a new directional strategy in its own Binance
USD-M Futures subaccount. It does not execute the existing LONG paper alerts or
pump-fade alerts. Railway continues to own Telegram polling, paper Futures,
fade warnings and Alpha. AWS owns the new scanner and execution service;
Supabase holds its independent journal, controls and heartbeat.

Initial allowlist: BTCUSDT, ETHUSDT, SOLUSDT, BNBUSDT, XRPUSDT. Closed 15m and 1h
symbol/BTC trends must agree. A recent 15m breakout needs above-baseline volume,
a later distinct closed 1m retest and reclaim, and aligned taker buying/selling.
The strongest confirmed candidates are checked first. No countertrend entries,
hedging, averaging down or automatic reversal. Missing/stale data withholds
entries and each symbol's scanner reason appears in `/futuresauto`.

## Account and order limits

- Up to five active intents; one position per symbol; 30-minute symbol cooldown.
- Isolated 2x; max $150 notional per position; total planned margin at most 50%
  of equity; aggregate modeled stop risk at most 3% of equity.
- Whole-position LIMIT target approximately $5 net after modeled fees/slippage.
  This closes the whole position, with no partial runner. Funding is additional.
- Planned stop is structural and never widened to meet a dollar risk budget.
  Entry sizing reserves 0.15% adverse entry slippage and 0.05% exit slippage.
  Modeled loss is capped at **min($5, 1% equity)**. At $100 equity the maximum
  modeled loss per entry is $1, not $5. Gaps/fills may exceed this estimate.
- When estimated open profit reaches half the original modeled loss, tighten
  the native stop to fee/slippage-adjusted break-even, if the quote permits it.
  This reduces exposure to giveback but cannot guarantee a break-even fill.
- Daily 2% net loss / realized giveback lock (Dubai reset), two-loss cooldown
  four hours, verified income/fees, funding and high-impact event checks.
- Five positions is a maximum, not a quota. Smaller capital, exchange minimums
  and shared risk budgets often permit fewer. At $150 notional, a $5 target
  needs more than a 3.3% price move after costs; it is not a quick scalp promise.

## Install once

1. Create a **new dedicated Binance subaccount**. Enable USD-M Futures,
   One-way Mode and Single-Asset Mode. Keep it free of manual/other-bot trades.
   Create a Futures/read-enabled API key restricted to the AWS public static
   outbound IP. Do not enable transfers/withdrawals for this worker.
2. In Supabase SQL Editor run `sql/futures_auto.sql`. It creates independent
   `nexio_futures_*` tables and lease/control RPCs. Both environments start
   with requested entries paused. Existing fade/paper tables are not changed.
3. Update the code on AWS. Since code is shared with the fade service, pause
   new fade entries for the update and verify its existing protections first.
   Never stop a worker with unprotected live positions.

```bash
cd /opt/nexio
sudo git -C /opt/nexio pull --ff-only origin main
sudo npm ci --omit=dev
sudo cp /opt/nexio/deploy/futures-worker.env.example /etc/nexio-futures.env
sudo chown nexio:nexio /etc/nexio-futures.env
sudo chmod 600 /etc/nexio-futures.env
sudo nano /etc/nexio-futures.env
```

Fill the new file with the new subaccount API keys, existing Supabase URL and
service-role key, BOT_TOKEN and OWNER_CHAT_ID. Never paste secrets into Telegram,
GitHub or ChatGPT. There is no fallback to BINANCE_API_KEY/SECRET used by fade.
The configuration requires your explicit separate-subaccount confirmation.
Different API keys alone cannot prove two accounts differ; create the new key
inside the new subaccount. Runtime pins the API-key fingerprint and rejects
unexpected key rotation; rotation requires flat verified accounts and deliberate
migration, not automatic adoption of another account's positions.

Testnet is the example default. Demo and live keys are different. For **live**
use the new real subaccount key and set in this file:

```dotenv
FUTURES_AUTO_ENVIRONMENT=live
ENABLE_FUTURES_AUTO=true
FUTURES_ACCOUNT_CONFIRMATION=SEPARATE_FUTURES_SUBACCOUNT
FUTURES_AUTO_LIVE_ACKNOWLEDGEMENT=I_ACCEPT_LIVE_FUTURES_ORDERS
```

This acknowledgement authorizes live orders; it does not certify a profitable
strategy or completed exchange drills. Changing ENABLE_FUTURES_AUTO to false
withholds new entries while the running service still reconciles/protects its
owned positions. Keep its credentials and live acknowledgement configured.

```bash
cd /opt/nexio
sudo /usr/bin/node --env-file=/etc/nexio-futures.env scripts/futures-auto-preflight.js
sudo cp /opt/nexio/deploy/nexio-futures.service /etc/systemd/system/nexio-futures.service
sudo systemctl daemon-reload
sudo systemctl enable --now nexio-futures
sudo systemctl status nexio-futures --no-pager -l
sudo journalctl -u nexio-futures --since "2 minutes ago" --no-pager
```

Preflight is read-only: it verifies account permissions/modes, balance, tables
and ownership; it never sends test/live orders or changes margin settings. If
it fails, fix the reported error before starting/resuming. Worker pins the
account key and claims its own `live:directional` or `testnet:directional` lease.

4. On Railway add only `FUTURES_AUTO_ENVIRONMENT=live` (or `testnet`, matching
   AWS), then deploy this version. No new Binance secrets belong on Railway.
5. Telegram `/futuresauto` should show a fresh separate worker heartbeat and
   successful reconciliation. Then `/futuresresume` requests new entries.
   Run `/futuresauto` again to verify acknowledgement. `/futurespause` stops
   new entries and keeps protection running; `/futurescloseall` pauses and
   closes only verified bot-owned positions in the **new** subaccount.
   Existing `/fade*` commands control only fade. Global `/pause` controls the
   original Railway scanner; use `/futurespause` for this independent worker.

## Recovery and validation

Intent and deterministic client order ID are saved before mutation. Unknown
entry responses are queried by ID and never blindly resubmitted. Definite
rejections retire without a phantom position. Unknown/missing accepted-order
state blocks further entries and requires inspection; do not delete a journal
or release a lease to make it trade. New stops are verified before old stops
are canceled. Profit orders and emergency exits are reduce-only; native stops
use closePosition. Wrong-direction/unowned positions are never adopted.

If protection cannot be installed/verified after a confirmed fill, an owned
reduce-only emergency exit is requested. If Supabase fails at that moment,
the exit can bypass the failed persistence path only for freshly verified bot
quantity. Native stops are the first protection; worker/Internet outages can
still disrupt updates, exits and reporting. A heartbeat proves liveness, not
that an exchange exit filled. Inspect Binance when an error is reported.

Automated tests exercise both directions, stop-before-target, partial profit
fills, restart recovery, ambiguous/rejected entries, pause/control failure,
lease loss, actual-fill budget overruns, unmanaged positions, break-even and
account isolation. They mock Binance. **No real demo/live fill, stop trigger,
restart drill or out-of-sample profitability test was run by this change.**
The strategy is experimental; the existing paper cohort does not validate it.
