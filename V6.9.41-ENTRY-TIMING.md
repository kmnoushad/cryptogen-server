# v6.9.41 entry timing and execution quality

This is an execution-quality repair, not a validated profitable strategy rebuild.
The existing strategy studies remain negative or inconclusive. No win-rate claim
or profitability claim follows from unit tests.

## Changes

- Railway Pump Fade scans are scheduled at each closed minute plus 1.5 seconds,
  instead of retaining the server-start offset. Startup still performs an immediate
  scan. Slow scans never overlap or replay missed intervals. Network and processing
  latency can still delay actual handoff and fills.
- AWS Futures uses a closed-minute scan key and 1.5-second close grace. This removes
  the additional elapsed-60-second drift. The existing five/ten-second worker poll
  can add latency; protection still runs before scanning on every tick.
- Both executors skip new entries when modeled round-trip fees and stop-exit
  slippage exceed 25% of modeled stop loss. Actual commission rates are used.
  This ceiling is an operational policy, not a statistically optimized parameter.
- Favorable price travel since confirmation cannot exceed the smaller of 0.15%
  of confirmation price and one quarter of current structural stop distance.
  Stops are never widened to satisfy the test. Existing spread/freshness rules remain.
- Ordinary Fade expiry, spread, extension and minimum-size rejection are per-signal
  skips. They do not emit a protection/reconciliation failure or poison the next entry.
  Exchange, lease, invalid-account and protection failures still fail closed.

The same confirmed-entry detectors remain executable. Early WATCH observations
remain informational. This release does not remove daily risk limits, raise leverage,
enable hedging, or manufacture trades. In particular, the Futures detector still
requires a closed 15-minute breakout and a later distinct one-minute retest/reclaim;
it cannot enter at the beginning of that breakout. Replacing this model requires
new out-of-sample evidence rather than relabeling an early warning as a proven entry.

## Deployment

Merge the PR into GitHub main for Railway deployment. Confirm Railway deployment
success; only Railway loads the Pump Fade scanner scheduling change.

On AWS, update the working copy without discarding local edits or stopping protection
for the duration of download/install. If tracked local edits exist, stop the update
and preserve them before pulling; do not reset or clean the repository.

```bash
cd /opt/nexio
sudo git diff --exit-code && sudo git diff --cached --exit-code && sudo git pull --ff-only origin main
sudo npm ci --omit=dev
sudo /usr/bin/node --test test/entry-quality.test.js test/fade-execution.test.js test/futures-auto.test.js test/pump-fade.test.js test/detection-audit.test.js
```

Only after the update and checks succeed:

```bash
sudo /usr/bin/node --env-file=/etc/nexio-fade.env scripts/fade-preflight.js && sudo systemctl restart nexio-fade
sudo /usr/bin/node --env-file=/etc/nexio-futures.env scripts/futures-auto-preflight.js && sudo systemctl restart nexio-futures
sudo journalctl -u nexio-fade -u nexio-futures --since "2 minutes ago" --no-pager
```

Check `/fadeauto` and `/futuresauto` for fresh heartbeat, completed reconciliation
and the entry-quality line. Existing entry controls remain in effect. A running
worker and passing read-only preflight do not prove order acceptance or an edge.
