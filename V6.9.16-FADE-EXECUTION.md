# v6.9.16 — opt-in Binance pump-fade execution

Implementation delivered disabled. Automated tests use an exchange double;
no credentialed demo orders, live orders or Supabase migration were run while
building this release. This is not an exchange-tested production rollout yet.
Use demo acceptance tests below before enabling live capital.

## Agreed account rules

- Trade only newly delivered pump-fade warnings, short direction, up to three
  simultaneous positions/intents. Never force three entries or replay old alerts.
- Intended allocation $250; isolated margin at 2x, at most $150 entry notional
  per coin and $450 aggregate notional for entry checks. At full size, initial
  margin is at most $225, leaving $25 of the intended allocation unallocated.
- Size downward using resistance plus 0.1%, the $5 cost-adjusted loss budget,
  available margin, and exchange quantity/price/notional filters. Entry must
  remain within 0.5% of the warning price, spread <=10 bps, warning <=90 seconds
  old and the final quote <=5 seconds old. Unsizeable setups are skipped.
- Initial exchange STOP_MARKET targets $5 loss using actual entry fills, quoted
  commissions and a five-basis-point stop slippage reserve. Stops trigger on
  CONTRACT_PRICE with price protection off to avoid deliberately delaying the
  trigger. Actual slippage/funding can exceed this budget.
- Resting reduce-only BUY LIMIT closes approximately 75%, rounded down to a
  quantity increment. Its target recovers the entire original estimated entry
  commission plus exit commission and aims to book $3 net. Maker/taker rates use
  the higher nonnegative quoted rate. Funding, fee changes and rebates can change
  realized cash PnL. No probability of profitability is claimed.
- After the partial order is fully filled, protect the remainder at fee-adjusted
  break-even, then trail 0.75% above the lowest ask observed by the monitor.
  The stop only tightens. New stops are verified before older stops are canceled.
  Tiny partial/runner quantities fail sizing; exact 75% is not always possible.

Only this executor uses signed Binance endpoints. Existing Futures/Alpha FIRE,
paper monitoring and market-mood reports do not submit orders. Warning-only
behavior remains the default. Neither the BTC long gate nor paper risk limits
control this short executor. There is no additional daily-loss circuit breaker:
three simultaneous $5 losses equal $15 (6% of $250), and later trades can lose
more. API-enforced isolated margin is not a promise that the account is safe.

## Account and Railway preparation

1. Use a dedicated Binance Futures account/subaccount, One-way mode and
   Single-Asset mode. Do not combine manual positions/orders or another bot on
   this account. The executor detects unrelated positions/orders and withholds
   entries; it does not switch global account modes or adopt manual trades.
2. Run `sql/fade_execution.sql` in Supabase SQL Editor. It creates a separate
   backend-only runtime table and lease/save RPCs. Use the backend service-role
   key already configured for the bot; do not expose it to client applications.
3. Create API credentials for Binance Demo Futures first. Put the key and secret
   directly in Railway variables. Never send credentials through chat, commit
   them, or include them in screenshots. For live credentials, enable only the
   needed read/Futures trading permissions, leave withdrawals disabled and
   restrict access to your deployment's outbound IP where supported. Verify the
   outbound address remains stable before relying on an IP restriction.
4. Keep one Railway replica. The database lease protects overlapping deploys,
   but a single instance is the intended operating configuration. Retain the
   same Supabase database and account for recovery; do not clear runtime state.

Required demo acceptance: verify SELL fills, isolated 2x margin, the native
close-all stop and reduce-only 75% limit on Binance; observe partial fills and
the runner stop; redeploy with an open demo position and confirm no duplicate
entry; exercise /fadepause and /fadecloseall. Check actual realized PnL in
Binance, including fees and funding. Passing unit tests/preflight alone does not
verify these exchange behaviors or strategy profitability.

Only after those checks, a deliberate live activation uses:

alone enables live execution. No credentials are printed by the signed client.

## Controls and recovery

- `/fadeauto`: environment, active intents, phases, stop/target and last error.
- `/fadepause`: persistently stop new entries while continuing protection.
- `/faderesume`: reconcile first, then permit new qualifying entries.
- `/fadecloseall`: persistently pause entries and request closes of bot-owned
  positions, then clean up bot orders. It does not close unrelated positions.
- Existing `/pause` also withholds entries; the separate exit monitor continues.

The monitor runs every five seconds when available; account-wide audits are
throttled to once a minute but always run before entries. Orders are recorded
before submission with stable client IDs. Unknown entry acceptance is queried
by ID and NEVER blindly resubmitted. An unresolvable intent holds a slot and
withholds further entries until manually investigated. Do not delete an intent
just to unblock trading: first establish its order/fill/position state on Binance.
The runtime persists profit/stop IDs so restart recovery can reconstruct stages.

Protection failures request a reduce-only market flatten. An uncertain exit can
be retried against a fresh verified position because reduce-only cannot open a
reverse position. If persistence fails after a verified entry, the emergency
path can send a uniquely tagged reduce-only BUY without a database write; it
never permits an unjournaled entry. If Binance is unreachable, closure cannot
be guaranteed. API errors are reported to Telegram and /fadeauto.

When Railway is down or execution is disabled, existing native stops and profit
limits remain on Binance, but software runner-stop updates cease. During the
small interval between entry and confirmed stop placement, the position is not
yet protected. There is no atomic entry-plus-bracket API assumed here. If the
bot is offline when the partial fills, its previous exchange stop remains until
recovery. /fadecloseall requires a working API and reconciliation; check Binance
directly during an outage. Repeated failures may require manual intervention.

The runtime is coordination state, not a full accounting ledger. /fadeauto does
not claim realized profit totals. Binance trade history is the source for live
realized PnL. Software tests do not measure market performance.
