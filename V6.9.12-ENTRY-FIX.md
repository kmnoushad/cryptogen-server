# v6.9.12 — revalidate waiting reclaim entries

## Problem and reproduction

A candidate previously confirmed as reclaimed could wait up to three closed bars
for spread/depth/impact recovery. During that wait, its original flow, volume,
open-interest and profile-specific momentum tests were not rechecked. A weaker
50% one-bar taker-buy ratio / zero delta check was sufficient once the book recovered.

The reproduction used LIQUID_TREND, negative EMA20 slope, price below EMA20,
negative five-minute return, 0.3x volume, 50% taker buying and -2% OI change.
The old code returned SIGNAL for a previously reclaimed candidate while the same
conditions returned HOLD before confirmation. The corrected code returns HOLD.
This establishes a code path, not attribution of any particular historical loss.

## Change

Before a waiting candidate may FIRE, reapply its existing configured flow,
volume, extension and OI requirements, plus its profile-specific momentum rule.
LIQUID_TREND retains its existing EMA slope/price/recent-move and multi-bar flow
checks. FAST_BREAKOUT and STEADY_MOMENTUM retain their existing profile semantics;
this patch does not invent additional momentum thresholds for those profiles.

Failure returns HOLD with explicit `post-reclaim` reasons. A recovered candidate
can signal before its original deadline, without another breakout candle. The
deadline does not restart. Structural failures and timeout still reject. Fresh
book-price ceiling/floor checks remain in force.

New trade setup JSON stores `entryValidationModel: revalidated-reclaim-v1` and
`entryRevalidatedAfterWait` for later attribution. No schema migration is needed.
Existing open trades retain their original exit rules; historical rows are untouched.

## Deployment and measurement

Merge and redeploy, then confirm `/version` reports **6.9.12**. Keep the existing
`PAPER_MODE=true` and `PAPER_100_TEST=true` settings for the virtual-$100 experiment.
Use `/diagnostics` to inspect new post-reclaim HOLD reasons and `/paperstats` to
track the virtual ledger. No Binance API key or new variable is required.

The paper account continues its existing balance/history; `/paperstats` is not reset
by this release. For evaluating the entry fix, separate newly tagged trades from
earlier entries using `setup.entryValidationModel`. Aggregate historical statistics
alone cannot measure the effect of this change.

BTC gating, universe selection (including the 24-hour gain cap), profit targets,
funding assumptions and the calendar API issue are outside this patch. This fix
may reduce FIRE frequency. It does not demonstrate profitable trading or establish
that changing the BTC/universe filters would improve performance.

## Verification

`npm run check`: regression cases for the reproduced stale confirmation, independent
flow/multi-bar flow/momentum/volume/extension/OI failures, missing OI, recovery without
a new breakout, unchanged deadline expiry, and fast/steady profile revalidation.
An engine-level regression confirms deteriorated OI creates no database trade and
sends no FIRE. Existing paper-ledger, exit-monitor and entry tests also pass.
