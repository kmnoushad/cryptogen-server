# NEXIO v6.9.0 — Futures funnel repair + Fast-Mover pump radar

v6.9.0 fixes the silent Futures funnel (thousands of evaluations, zero FIREs) and adds an
independent live "sudden pump" radar. No terminal manipulation gate was weakened; Alpha,
calendar, and store schemas are untouched; no SQL migration is required.

## Root cause: why Futures never FIREd

Live gate telemetry showed the funnel dying at three places:

1. **BTC gate long-only + fail-closed.** Any BTC data error or sub-EMA50 drift sets
   `btc.allowed = false`, which silently blocks every arm (`BTC_BLOCK`) and cancels active
   candidates — with zero outward visibility. Operators could not tell a frozen bot from a
   calm market.
2. **Hardcoded reclaim taker-flow thresholds.** `strategy.js` required `buyRatio1 ≥ 0.57` and
   `deltaRatio1 ≥ 0.14` (liquid path 0.54/0.08) on the reclaim bar. On deep, market-maker-heavy
   perpetuals a healthy reclaim typically prints 0.52–0.56 buy ratio, so candidates reclaimed
   structurally but kept HOLDing on `taker flow weak` until TTL expiry.
3. **Execution depth gates calibrated for top-5 liquidity.** `$100k` each side within 0.5% and
   `0.75` bid/ask imbalance reject most of the rotating 60-symbol universe even during orderly
   conditions.

## Gate changes (old → new default)

| Gate | Env var | Old | New |
| --- | --- | --- | --- |
| Min depth each side (0.5%) | `MIN_DEPTH_EACH_SIDE_USD` | 100,000 | **50,000** (min 10,000) |
| Min entry depth imbalance | `MIN_ENTRY_DEPTH_IMBALANCE` | 0.75 | **0.60** (range 0.4–1.5) |
| Reclaim min taker buy ratio | `FUTURES_RECLAIM_MIN_BUY_RATIO` | hardcoded 0.57 | **0.55** (range 0.50–0.70) |
| Reclaim min delta ratio | `FUTURES_RECLAIM_MIN_DELTA_RATIO` | hardcoded 0.14 | **0.10** (range 0–0.30) |

- The liquid-trend path keeps its historical relaxation: buy ratio = cfg − 0.03, delta = cfg − 0.06
  (hardcoded 0.57/0.14 → liquid 0.54/0.08), floored at 0.50 / 0.06. With the new defaults that is
  0.52 / 0.06.
- `context.risk.terminalRisk` handling is byte-for-byte equivalent; crash, sell-delta climax,
  OI divergence, and depth-collapse-plus-spread-widening remain terminal rejections.

## BTC-freeze visibility (A2)

- Engine tracks `btcBlockedSince` while `btc.allowed === false` and counts candidates cancelled
  by the gate.
- New env `BTC_BLOCK_HEARTBEAT_MIN` (default **120**, `0` = off). After the gate has been closed
  continuously for ≥ N minutes, the bot sends ONE Telegram message and persists a
  `FUTURES_BTC_BLOCK_HEARTBEAT` event (dedup key
  `futures:btc-block-heartbeat:{blockStartBucket}:{elapsedWindowIndex}`, block-start anchored so a
  restart inside the same window cannot double-notify). Payload: regime, EMA50 distance,
  slope6h, top-3 gate counts, cancelled-candidate count. Repeats at most once per N-minute window.

## `/why` owner command (A3)

Answers "why is the bot quiet?" in one reply: BTC regime with numeric EMA50 detail and how long
the gate has been closed, whether the account risk snapshot allows entries (with reasons), top-5
pre-arm `IMPULSE:` blockers, top-5 candidate HOLD reasons, top-5 REJECT reasons, current
candidates with state, and the Fast-Mover detector status line.

## Fast-Mover (sudden pump) detector (B) — `src/pump-detector.js`

Independent of the slow closed-candle funnel; catches violent Binance USDT-M pumps in near real
time. **Informational-actionable alert only — it never opens a database trade.**

- Feed: `wss://fstream.binance.com/stream?streams=!miniTicker@arr` (~1s, all symbols); per-symbol
  ring buffer of `{ t, price, q }` over a 10-minute horizon, capped at 700 points.
- Volume velocity: 60s delta of the rolling 24h quote volume versus the median of the same 60s
  deltas sampled every 30s over the previous 9 minutes (soft gate; REST klines hard-confirm).
- Trigger (all required; defaults in parentheses): 60s move ≥ `FAST_MOVER_MIN_1M_PCT` (**0.8**) OR
  180s move ≥ `FAST_MOVER_MIN_3M_PCT` (**1.5**); volume acceleration ≥
  `FAST_MOVER_VOLUME_ACCEL` (**3.0**) × positive baseline; 24h quote ≥
  `FAST_MOVER_MIN_QUOTE_USD` (**$10M**); symbol not in `FUTURES_EXCLUDED`, not BTC, live price;
  realtime shock guard not blocked; engine not paused; per-symbol cooldown
  `FAST_MOVER_COOLDOWN_MIN` (**30**) and global `FAST_MOVER_MAX_ALERTS_PER_HOUR` (**6**);
  master switch `ENABLE_FAST_MOVER_ALERTS` (default **true**).
- Confirm-before-alert via the existing `BinanceClient`: closed 1m klines (limit 5) must show the
  up move with taker buyRatio ≥ 0.52; depth (limit 20) spread ≤ `FAST_MOVER_MAX_SPREAD_BPS`
  (**30**, informational, looser than the entry gate). Confirm failure stays silent and increments
  `confirmRejected`.
- Alert: `[FUTURES] ⚡ FAST MOVER` with symbol, move %/window, price, volume acceleration ×, 1m
  taker buy %, spread, 24h volume, and an explicit caution line (live radar ping, not the gated
  FIRE entry). Persists `FUTURES_FAST_MOVER` to `nexio_events` with dedup key
  `fast-mover:{symbol}:{cooldownBucket}`; a DB failure never silences the alert.
- Robustness mirrors `realtime-shock.js`: reconnect with 1s→30s exponential backoff, 30s staleness
  watchdog, unref'd timers, clean `stop()`, `health()` (enabled, connected, lastMessageAt, tracked
  symbols, metrics, lastError), and injected `WebSocketImpl`/`now`/`sleepImpl` for tests.
- Metrics: `triggers`, `alerts`, `confirmRejected`, `dedupSkipped`, `suppressed`
  (cooldown/cap/shock/paused).
- Wiring: `index.js` constructs the detector, starts it after `engine.initialize()`, stops it in
  shutdown, and passes it into `Engine` (like `realtimeShock`) so `/status`, `/why`, `/health` and
  scan-time pause state can read it. Engine never imports the detector module; `pump-detector.js`
  imports `FUTURES_EXCLUDED` from `engine.js` — verified acyclic.

## Review hardening (post-review fixes)

- **Fast-mover dedup before alert.** `confirmAndAlert` now persists the `FUTURES_FAST_MOVER`
  event FIRST and honours the store's 409 dedup signal (`insertEvent → false`): a restart that
  wiped in-memory cooldowns no longer produces a duplicate Telegram alert for the same cooldown
  bucket — the send is skipped and a new `dedupSkipped` metric increments. A DB ERROR (throw)
  keeps the documented behaviour: log the persistence failure, still send the alert.
- **Failed-confirm throttle.** A symbol whose REST confirm failed used to re-fire a full confirm
  flight every 1s tick while it hovered past the price/volume gates. A `lastConfirmAttempt` map
  now enforces a 60s minimum gap between confirm flights per symbol, stamped when a flight
  STARTS so in-flight and just-failed attempts are both throttled (counts under
  `suppressed.cooldown`).
- **BTC-block heartbeat boundary double-fire.** Epoch-aligned buckets
  (`Math.floor(now/windowMs)`) could fire twice ~one scan apart when the first fire landed at
  the end of one bucket and the next scan crossed into the next. Firing is now anchored to
  elapsed time: fire only when `now - btcBlockedSince >= windowMs` AND
  `now - lastBtcBlockHeartbeatAt >= windowMs`; both timestamps reset when `btc.allowed` flips
  true. The persisted dedup key is now block-start anchored:
  `futures:btc-block-heartbeat:{blockStartBucket}:{elapsedWindowIndex}`.
- **Stale-socket close guard.** The miniTicker `close` handler now returns early when the closing
  socket is not the current one, so a stale socket's close cannot mark a healthy replacement
  disconnected or schedule a spurious reconnect.
- **Liquid delta relaxation corrected.** The comment and floor logic said 0.04; the historical
  relaxation is 0.06 (0.14 → 0.08). Liquid delta min is now `max(0.06, cfg − 0.06)`; buy stays
  `max(0.50, cfg − 0.03)` — defaults still yield buy 0.52 / delta 0.06 for the liquid path.
- **Depth-imbalance fallback aligned.** The inline `cfg.minEntryDepthImbalance ?? 0.75` fallback
  in `strategy.js` is now `?? 0.60`, matching the v6.9 config default.
- Tests: 91 → 94 (all green). New coverage: dedup-skip alert suppression, failed-confirm
  throttle, heartbeat bucket-boundary double-fire + block-start re-anchor after regime flip.

## v6.9.2 boot-resilience hotfix

Production crash: an out-of-range `BTC_BLOCK_HEARTBEAT_MIN` in Railway made `loadConfig` throw,
killing the entire service at startup. An operator typo in an *optional* tuning variable must
never prevent the bot from booting.

- All ten v6.9 optional tuning knobs (`FUTURES_RECLAIM_MIN_BUY_RATIO`,
  `FUTURES_RECLAIM_MIN_DELTA_RATIO`, `BTC_BLOCK_HEARTBEAT_MIN`, `FAST_MOVER_MIN_1M_PCT`,
  `FAST_MOVER_MIN_3M_PCT`, `FAST_MOVER_VOLUME_ACCEL`, `FAST_MOVER_MIN_QUOTE_USD`,
  `FAST_MOVER_COOLDOWN_MIN`, `FAST_MOVER_MAX_ALERTS_PER_HOUR`, `FAST_MOVER_MAX_SPREAD_BPS`)
  now parse leniently: an invalid or out-of-range value logs a loud `[CONFIG WARNING]` and
  falls back to the safe default instead of throwing. `ENABLE_FAST_MOVER_ALERTS` behaves the
  same (invalid → warning → default `true`).
- Required secrets (`BOT_TOKEN`, `OWNER_CHAT_ID`, `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`)
  and all pre-v6.9 variables keep the original strict fail-fast validation.
- Regression test reproduces the exact production crash value and asserts fallback + warning.

## v6.9.3 Alpha Fast-Mover radar + QUALIFIED runner fix

Motivation: Binance Alpha tokens can go vertical long before the guarded AlphaRadar pipeline
reacts — it needs ≥3 snapshots (~12 min at 240s polling) before qualification, and it demoted
QUALIFIED tokens back to SEEDED once `change24h` crossed +40, abandoning exactly the strongest
runners (observed example: APR +163% in ~18h). v6.9.3 adds an independent fast radar and fixes
the demotion.

**Workstream A — `src/alpha-mover.js` (new `AlphaFastMover`).** Informational-actionable early
alert on the same `ALPHA_URL` feed as `src/alpha.js` (constant + token parser reused, not
duplicated). NO database trade row, NO outcome monitoring, NO change to AlphaRadar's IGNITION
logic, and deliberately no check for an open alpha trade / IGNITED state — the radar is
independent by design.

- Per-token ring buffer (`{ t, price, liquidity, holders }`, keyed
  `chainId:contractAddress.toLowerCase()`, 60-min horizon, 120-point cap), fed by a
  `cfg.alphaMoverPollMs` (90s) polling loop; errors are logged/counted and the loop keeps going.
- Hard floors reuse existing cfg keys (price > 0, `alphaMoverMinLiquidityUsd`,
  `alphaMinVolumeUsd`, `alphaMinHolders`); tokens outside the 24h window
  (`>= alphaMoverMax24hChangePct`, default +60, or `<= -20`) are skipped.
- Trigger: +3% vs the 10-minute reference OR +6% vs the 30-minute reference. The reference is
  the latest buffer point at-or-before `now − window` with a staleness cap of two poll
  intervals; insufficient history means no trigger — a reference is never fabricated.
- Soft confirmation: liquidity ≥ −3% vs the 30-min reference (when available) and holders not
  decreasing vs the previous point.
- Suppression: engine `/pause` (injected `isPaused`), 60-min per-token cooldown, 4-alerts/hour
  global cap.
- Security screen (GoPlus, same `fetchAndAssessOnchain`) runs BEFORE alerting:
  `hardBlock` or `riskScore > 5` stays silent (metric `blocked`); a provider throw fails safe
  (metric `errors`, no alert); POSSIBLE_RUG/CAUTION ratings alert with a ⚠️ label.
- Dedup mirrors the v6.9.1 futures detector exactly: the `ALPHA_FAST_MOVER` event is inserted
  FIRST (key `alpha-mover:{key}:{cooldown bucket}`); `insertEvent → false` ⇒ log +
  `dedupSkipped`, no Telegram; a DB throw ⇒ log, still send.
- Wired in `index.js` exactly like the v6.9 fastMover (constructed after engine, `isPaused`
  injection, `start()` after `engine.initialize()`, `stop()` in shutdown, one startup-message
  line). `engine.js` accepts the `alphaMover` instance, exposes its `health()` and adds one
  line to `/status` and `/why`; it never imports `alpha-mover.js`.

**Workstream B — QUALIFIED runner fix (`src/alpha.js`, minimal).** `eligible()` is split into
hard floors (price > 0, volume24h, liquidity, holders, `change24h > -20`) versus the heat cap
(`change24h < 40`). Demotion of a QUALIFIED token now happens ONLY on hard-floor failure; the
heat cap still blocks NEW SEEDED→QUALIFIED transitions (conservative entry preserved), and a
QUALIFIED runner riding past +40% keeps its window and can still complete IGNITION if the
since-qualified move and second security check pass. No scoring or ignition thresholds changed.

**New env vars** (all optional, lenient-parsed via the v6.9.2 warn-and-fall-back pattern):

| Var | Default | Range |
| --- | --- | --- |
| `ENABLE_ALPHA_FAST_MOVER` | `true` | bool (invalid → warn → `true`) |
| `ALPHA_MOVER_POLL_MS` | `90000` | 45_000–600_000 |
| `ALPHA_MOVER_MIN_10M_PCT` | `3.0` | 0.5–20 |
| `ALPHA_MOVER_MIN_30M_PCT` | `6.0` | 1–40 |
| `ALPHA_MOVER_MAX_24H_CHANGE_PCT` | `60` | 20–200 |
| `ALPHA_MOVER_COOLDOWN_MIN` | `60` | 5–720 |
| `ALPHA_MOVER_MAX_ALERTS_PER_HOUR` | `4` | 1–30 |
| `ALPHA_MOVER_MAX_RISK_SCORE` | `5` | 0–10 |
| `ALPHA_MOVER_MIN_LIQUIDITY_USD` | `150000` | ≥25_000 |

**Deployment:** no SQL migration — only `nexio_events` inserts with the new
`ALPHA_FAST_MOVER` event type / `alpha-mover:*` dedup keys. All vars optional; safe defaults
apply when unset. No new npm dependencies.

Tests: 95 → 121 (all green). New coverage: ring-buffer reference/staleness, every floor and
24h gate, 10m vs 30m windows, soft confirmations, cooldown, hourly cap, pause suppression,
hardBlock/riskScore silent blocks, ⚠️ label, security-throw fail-safe + recovery, dedup-hit
no-send, DB-error still-sends, fetch-failure resilience, health shape, start/stop idempotence,
config defaults + lenient fallback, and the three runner-fix behaviours in AlphaRadar.

Review hardening (follow-up): `pollOnce()` has a re-entrancy guard (`this.polling`, returns
`{ skipped: 'already running' }` while a poll is in flight, cleared via try/finally) so
overlapping ticks can never double-send at a cooldown-bucket boundary; expired entries are
pruned from the `cooldowns` map during each poll; the hourly-cap timestamp is pushed only
AFTER a successful Telegram send (a dedup-skipped or send-failed alert no longer burns a
slot; the pre-send per-token cooldown is unchanged); and the reference staleness cap is
clamped to `min(2 × alphaMoverPollMs, 5 min)`. Tests: 121 → 126 (all green).

## v6.9.4 Tier-2 TRENDING MOVER radar + suppression observability

Motivation: the v6.9 fast-mover detector (tier 1) only fires on violent bursts — +0.8%/60s or
+1.5%/180s with ≥3× 60s volume acceleration, then a REST confirm (taker buyRatio ≥ 0.52,
spread ≤ 30 bps). Real 24h gainers often grind up over 15–60 minutes on thinner books — no
burst at all, or the tier-1 confirm rejects the wider spread — so the radar stayed silent on
exactly the moves visible in the Gainers tab. v6.9.4 adds a second, independent detection tier
inside the same `FastMoverDetector` class (`src/pump-detector.js`): same WebSocket firehose,
same confirm/cooldown/dedup plumbing, fully separate maps and counters. Tier-1 burst behavior
is byte-equivalent (all v6.9.1–v6.9.3 pump-detector tests pass unmodified).

**Workstream A — Tier-2 "TRENDING MOVER".**
- Slow ring buffer per symbol: at most ONE point per 15s (decimated on ingest), 70-minute
  horizon, ~300-point hard cap; pruned like the fast buffer and reaped in the same watchdog
  pass. Tier 2 is evaluated only when a new decimated point lands — at most once per 15s per
  symbol, never per raw tick.
- Trigger (any one window): +2.0% vs ~15m OR +3.5% vs ~30m OR +5.0% vs ~60m, with a 5-minute
  volume acceleration ≥2.0× vs the median of 5-minute `q` deltas over the prior ~60 min (soft
  gate, baseline must be > 0), 24h quote volume ≥ `FAST_MOVER_MIN_QUOTE_USD`, not
  BTC/excluded, price > 0, shock guard clear, engine not paused. Window references use the
  latest slow point at-or-before the target with a staleness cap of min(2 × 15s, 60s) — a
  reference is never fabricated from too-old data.
- REST confirm (same injected binance): klines 1m×5 taker buyRatio ≥ 0.50, depth-20 spread
  ≤ 45 bps. Confirm failures are silent + logged, count `trendingConfirmRejected`, and
  re-attempts are throttled ≥120s per symbol via a map separate from tier 1's 60s throttle.
- Separate cooldown (`TRENDING_COOLDOWN_MIN`, 120) and hourly cap
  (`TRENDING_MAX_ALERTS_PER_HOUR`, 4) — a tier-1 alert never consumes tier-2 budget and vice
  versa.
- Dedup mirrors tier 1 exactly: `insertEvent` FIRST with event_type `FUTURES_TRENDING_MOVER`
  and key `trending-mover:{symbol}:{floor(now/(cooldownMin*60000))}`; `false` ⇒ log +
  `trendingDedupSkipped`, NO Telegram send; a DB throw ⇒ log, still send.
- Telegram: `[FUTURES] 📈 TRENDING MOVER` with symbol, move % + which window (15/30/60m),
  price, 5m volume accel ×, taker buy %, spread, 24h volume, and a caution line (steady mover
  — not a burst; can still reverse; radar ping, not a gated entry). Informational only: NO
  database trade row, ever.

**Workstream B — suppression observability.** Both tiers maintain per-reason suppression
counters (`cooldown, hourlyCap, shock, paused, volumeLow, quoteLow, confirmRejected,
dedupSkipped`; tier 1 keeps its historical `cap` key for the hourly cap). `health()` now also
exposes `suppressed`, `lastTriggerAt`, `lastAlertAt`, `lastSuppressedReason` and a `trending`
block (enabled, tracked symbols, tier-2 metrics + suppressed). `/why` renders 2–3 radar lines
(per-tier alerts/triggers plus the top-2 merged suppression reasons); `/status` shows one
compact line per tier.

**New env vars** (all optional, lenient warn-and-fall-back parsing; boot never aborts):

| Var | Default | Range |
| --- | --- | --- |
| `ENABLE_TRENDING_MOVER` | `true` | bool (invalid → warn → `true`) |
| `TRENDING_MIN_15M_PCT` | `2.0` | 0.5–10 |
| `TRENDING_MIN_30M_PCT` | `3.5` | 1–20 |
| `TRENDING_MIN_60M_PCT` | `5.0` | 1.5–40 |
| `TRENDING_VOLUME_ACCEL` | `2.0` | 1–10 |
| `TRENDING_MIN_BUY_RATIO` | `0.50` | 0.40–0.70 |
| `TRENDING_MAX_SPREAD_BPS` | `45` | 5–200 |
| `TRENDING_COOLDOWN_MIN` | `120` | 15–720 |
| `TRENDING_MAX_ALERTS_PER_HOUR` | `4` | 1–20 |

**Deployment:** NO SQL migration — only `nexio_events` inserts with the new
`FUTURES_TRENDING_MOVER` event type / `trending-mover:*` dedup keys. All vars optional with
safe defaults; no new npm dependencies; no changes to risk/strategy/store/calendar/alpha.
Tier 2 shares the tier-1 WebSocket, so it is active whenever `ENABLE_FAST_MOVER_ALERTS` is on.
